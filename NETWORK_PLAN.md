# NETWORK_PLAN.md — сеть и план MVP (только проект)
Без кода. Для Subnautica Mobile кооператива, 2+ игрока, телефоны без root/ПК.

## Варианты топологии

### Вариант 1 — один телефон = хост (P2P по LAN/VPN)  ★ РЕКОМЕНДУЕМ ДЛЯ MVP
- Хост = игрок, у которого запущен мир; клиенты подключаются к его IP:port.
- Discovery без ПК:
  - Общая Wi-Fi: хост показывает свой локальный IP (мод читает и показывает на экране), клиент вводит его в конфиг/поле.
  - Нет общей Wi-Fi: VPN-оверлей **Tailscale** или **ZeroTier** (ставится из Play, даёт виртуальные IP, работает через NAT). Хост и клиенты в одной tailnet → те же IP, что в LAN.
- Транспорт: **UDP + свой надёжный слой** (sequenced + ack + retransmit для важных), либо **ENet**-подобный. Для MVP достаточно UDP с простым reliable-каналом для событий и unreliable для позиций.
- Модель авторитета: **хост авторитетен** по миру (время, спавн, AI существ, предметы). Клиент авторитетен только по своему игроку (позиция/анимации), шлёт хосту, хост ретранслирует остальным.
- Плюсы: минимум движущихся частей, не нужен сервер, дёшево итеративно.
- Минусы: хост должен быть онлайн; при выходе хоста сессия падает; NAT без VPN не пробить.

### Вариант 2 — маленький relay-сервер (VPS)
- Все подключаются к дешёвому VPS (у пользователя уже есть VM), который гоняет UDP-пакеты между игроками (host-relay).
- Discovery: фиксированный адрес relay + комната по коду.
- Плюсы: работает без VPN и без общей сети, NAT не проблема.
- Минусы: +1 компонент для поддержки, задержка выше, надо держать relay запущенным. Подходит на этапе 2+ (когда базовый кооп уже работает в LAN).

### Вариант 3 — выделенный сервер (headless)
- Отдельный процесс, симулирующий мир. Для IL2CPP-игры без исходников — очень тяжело (нужно переиспользовать игровую логику).
- Для MVP НЕ рекомендуется. Реалистично только на далёкую перспективу.

## Транспорт / формат / частота (для варианта 1)
- Транспорт: UDP. Два логических канала:
  - Unreliable (позиции/анимации): 10–15 Гц, последнее состояние важнее старых.
  - Reliable ordered (события: чат, предметы, время, спавн): ack + retransmit.
- Формат пакетов: компактный бинарный (little-endian). Заголовок: [u8 type][u16 seq][u8 playerId]. Полезная нагрузка по типу. Никаких JSON по сети (только для конфига).
  - Пример позиции: type=0x01, playerId, pos(3×f32), rot(4×f32), animFlags(u16).
- Частота: позиции 10–15 Гц; события — по факту; keepalive 1 Гц; таймаут пира ~5 с.

## Сворачивание приложения / смена сети
- Android при сворачивании может усыпить процесс/сокеты. Нужен `WAKE_LOCK` (уже есть в манифесте) + foreground-service для хоста (разрешение FOREGROUND_SERVICE есть).
- Смена сети (Wi-Fi↔LTE): IP меняется → переподключение клиента к хосту по последнему известному адресу (или через Tailscale, где IP стабилен). Хост шлёт heartbeat; клиент при таймауте — reconnect.
- Хост при сворачивании: сессия на паузе/деградации; клиенты видят «хост недоступен».

## Рекомендация для MVP
Вариант 1 (P2P-хост + Tailscale для игры не в одной Wi-Fi). Минимум частей: только игра на двух телефонах + мод. Relay добавить позже как опцию.

## План MVP по этапам (критерии «готово» / «стоп»)
- **(0) Hello-world на телефоне.** Готово: мод пишет в лог «загрузчик жив», хук Player.Awake срабатывает, раз в ~5с координаты выводятся через ErrorMessage.AddMessage. Стоп/пересмотр: игра не стартует (PAIRIP/подпись) → решение по защите; или il2cpp API не резолвится.
- **(1) Призрак + ники + чат в одной сети.** Готово: два телефона, второй игрок виден как движущийся призрак с ником, сообщения доходят обе стороны. Стоп: нестабильный рендер призрака, дезсинк позиций, краши.
- **(2) Общее время/базовые события.** Готово: время суток совпадает (хост→клиенты через SetTimePassed). Стоп: расхождение времени, рассинхрон глобальных событий.
- **(3) Предметы и инвентарь.** Готово: подбор/выброс предмета виден обоим, инвентари согласованы, нет дюпа. Стоп: дюп/пропажа предметов, конфликт одновременного подбора (нужен арбитраж хостом).
- **(4) Сущности и постройки.** Готово: существа/транспорт/постройки синхронизированы. Стоп: нестабильные UniqueIdentifier между клиентами, непредсказуемый спавн (сид) — пересмотр протокола спавна.

## Честная оценка достижимости
- **Достижимо:** (0)–(2) при условии решения вопроса с PAIRIP (иначе мод не запустить). Призрак, чат, время — стандартно.
- **Сложно, но реально:** (3) предметы — основная боль = арбитраж и отсутствие дюпов.
- **Тяжело / под вопросом:** (4) сущности и постройки — зависит от детерминизма спавна и стабильности ID сущностей; AI существ проще держать авторитетным на хосте.
- **Главный блокер сейчас:** не сеть и не код, а PAIRIP — без решения по нему этап (0) не запустить.
